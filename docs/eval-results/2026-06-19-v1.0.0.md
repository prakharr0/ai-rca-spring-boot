## 1. TemperatureEvalTest

Single exception fixture (`throwable.txt` — NPE inside a multi-layered data pipeline), 10 reps per temperature.

| Temperature | Confidence avg | StdDev | Rank-1 title uniqueness | Rank-3 likelihood violations | Known pattern variants |
|-------------|----------------|--------|-------------------------|------------------------------|------------------------|
| 0.1 | 0.75 | 0.0000 | 1/10 — perfect | 0/10 | 1 — perfect |
| 0.3 | 0.75 | 0.0000 | 3/10 | 0/10 | 2 |
| 0.7 | 0.75 | 0.0000 | 3/10 | 1/10 | 4 |
| 1.0 | 0.75 | 0.0000 | 10/10 — every run different | 1/10 | 10 — completely unstable |

**Findings:**
- Confidence is locked at 0.75 regardless of temperature — the model is very certain about this score for this exception type. This is a property of the prompt + exception, not temperature.
- Rank-1 category (`Code`) is unanimous at all temperatures.
- Title uniqueness is the clearest temperature signal: 1 unique title at 0.1 vs 10 unique titles at 1.0.
- Rank-3 likelihood violations (expected `Low`) appear at 0.7 and 1.0 — the model occasionally promotes rank-3 to `Medium` at higher temperatures.
- `missingInformation` is empty at all temperatures — the model considers itself well-informed for this exception type.
- **Production recommendation: keep temperature at 0.1.** The degradation between 0.1 and 0.3 is minor; between 0.3 and 1.0 it is severe.

### Failed fixtures

**`class_cast_deserialisation` — category flip**

Run results:
```
run #0  Code       — Stale serialized object in cache
run #1  Code       — Stale serialized object in cache
run #2  Infrastructure — Stale object in cache   ← flip
run #3  Code       — Stale serialized object in cache
run #4  Code       — Stale serialized object in cache
```

The model produced `Infrastructure` on 1 out of 5 runs. The hypothesis is the same (stale cached object) but the model classified it once as an infrastructure concern (cache layer) rather than a code concern (missing cache invalidation). This is a genuine ambiguity — stale cache hits straddle both categories.

**`db_connection_timeout` — title wording variance**

Run results:
```
run #0  Configuration — Connection pool size insufficient for load
run #1  Configuration — Connection pool size insufficient for workload
run #2  Configuration — Connection pool size insufficient for load
run #3  Configuration — Connection pool size is insufficient for workload  ← 3rd variant
run #4  Configuration — Connection pool size insufficient for workload
```

Category was unanimous (Configuration=5/5) and the hypothesis is semantically identical across all runs. The 3 distinct titles are: "...for load", "...for workload", "...is insufficient for workload". This is a wording variance failure, not a conceptual one.

## Observations and Action Items

### Fixture `expectedCategory` corrections needed

Three fixtures have `expectedCategory` values that don't match the model's consistent output. The model is not wrong — these are ambiguous failure types and the fixtures need updating:

| Fixture | `expectedCategory` | Model's consistent answer | Decision                                                                                                                                                                                                                        |
|---------|-------------------|--------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `circular_bean_dependency` | `Code` | `Code` | Circular deps are a code structure issue, not a configuration one.                                                                                                                                                              |
| `http_4xx_downstream` | `Dependency` | `Code` | **Fixture kept.** Prompt defines `Dependency` as "external services, third-party APIs." Model is miscategorising a 404 from an external inventory API as a code issue. Prompt quality problem to address in a future iteration. |
| `http_timeout_downstream` | `Dependency` | `Infrastructure` | **Fixture kept.** A payment gateway timeout fits `Dependency` per the prompt definition. Model treating it as `Infrastructure` is a known model behaviour discrepancy, not a fixture error.                                     |

These don't affect structural or consistency test results (the category assertion only fires on flips, not mismatches with `expectedCategory`). The `expectedCategory` field is purely for human reference and quality annotation — it's not asserted in the current test code.

### Consistency failures to address

1. **`class_cast_deserialisation`**: Borderline Infrastructure/Code — the fixture is genuinely ambiguous. Either relax the consistency threshold for this fixture to allow 2 unique categories, or improve the fixture's stack trace to make the code root cause more obvious.

2. **`db_connection_timeout`**: Title wording variance with identical semantics — raise `MAX_UNIQUE_RANK1_TITLES` from 2 to 3 for this type, or accept that slight paraphrasing ("load" vs "workload") is fine and not a real eval failure.

### `proposedFix` follow-up

All `proposedFix` fields are `null` in these results because the prompt schema was updated after these runs. Re-run `RcaStructuralEvalTest` after installing the updated module to verify:
- `proposedFix` is non-null for all root causes
- Content is stack-trace-specific (not generic advice)
- Length is within 2 sentences
